## Setup for the infrastructure drill

1. In the source Supabase organization, open **Billing** and record the plan and existing project count. In the approved source project, open **Database → Backups**. Record the most recent usable snapshot, the oldest available recovery point, whether physical backups and PITR are enabled, and the source project region. Check **Storage** for a private bucket, any backup or versioning configuration, and its backing retention. Check **Integrations → Cron** for the expiry job and its recent results. Confirm the recovery point objective (maximum acceptable data loss) and recovery time objective (acceptable service interruption) with the founder.
2. Use a fictional-only source dataset. Provision a separate recovery target with a distinct project reference and credentials, in the approved region. Keep access with the approved operators and the test app on loopback or a separately authorized protected HTTPS environment. Use a private bucket and no production alias, SMTP, real OAuth accounts, webhooks, or jobs that can send external traffic. Review any extensions, integrations, and SQL before restore. Supabase physical clones copy the entire database and copied jobs can start automatically. A logical restore into an empty target gives the operator a chance to review those definitions before enabling any jobs. [Supabase clone limitations](https://supabase.com/docs/guides/platform/clone-project)
3. Create fictional verified owner, partner and unrelated identities. Save books, Memory Tree records, letters and journey documents with generated photographs and audio. Share selected items only, including an unopened scheduled letter. Write down expected document counts, backup time, attachment byte checksums and access results. Freeze writes during the small drill capture so the database and media have a common recovery point. Back up roles, schema and data with the supported Supabase procedure. Separately copy the private objects into encrypted private backup storage with a protected manifest that maps object keys to checksums and database snapshot time. A database backup alone includes Storage metadata and leaves out the file bytes. [Database backups](https://supabase.com/docs/guides/platform/backups) · [Backup and restore with the CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore)
4. Have another authorized operator verify the blank target project reference before restoring anything. Start the timer. Restore Auth identities, required roles, schema, grants, migrations, app data and sharing rows. Restore media bytes using the supported Storage/S3 interface, preserving bucket names, object paths and content types. Follow the provider procedure for Storage metadata so restored metadata without bytes does not cause upload conflicts. Apply custom Storage policies and Auth settings for the target, then point only the isolated app at it. Use fresh target credentials and fresh sessions. Keep database dumps, manifest details and restored files off Git, chat and provider log streams. [Supabase Storage downloads and file metadata](https://supabase.com/docs/guides/storage/management/download-objects)
5. As the owner, authenticate, read each restored workspace, compare revision counts, and open the photos and audio. Verify partner access to the selected book and its attachments, denial for the unopened letter body and private items, and denial following grant revocation and disconnection. Verify the unrelated and signed-out viewers cannot open restored records or receive private file bytes. Stop the timer after the checks. Record backup age, data size, restore and validation durations, transport or configuration failures, and the procedure for verified removal of the exercise copies under the approved retention rules. Leave service cutover to a separate decision.

## Monitoring and alert setup

1. Open **Vercel → Project → Logs** and **Observability**. Select the protected test environment. Review deployed function failures, current subscriptions, plan coverage, access and log retention. In **Supabase → Logs / Integrations**, check Auth, PostgreSQL, Storage and Cron failures and who can access the results. Keep provider dashboards limited to approved operators.
2. Have the founder approve an operational mailbox, an internal channel, or an existing incident system and name the primary and backup people. If available on the plan, use **Vercel → Observability → Alerts → Subscribe to Alerts** for a function 5xx anomaly notification and select the authorized destination. Use an existing approved filtered log monitor for application events where supported. Check that the monitor includes the protected Preview environment, as its managed alert coverage can differ from production. Do not create integrations or send external alerts without the destination approval. [Vercel Alerts](https://vercel.com/docs/alerts)
3. Begin in test with a five-minute window. Page for repeated `workspace.save_failed`, `database.unavailable`, `upload.stage_failed`, `auth.unavailable`, `storage.write_failed`, or `storage.read_failed`. Also alert on persistent function 5xx, consecutive failed isolated smoke checks, missed backup windows, and the expiry job missing two expected runs. Use trend or rate alerts for `auth.rejected`, `auth.rate_limited`, `upload.incomplete` and revision conflicts. Escalate `account.cleanup_failed` for operator follow-up without including an account identifier. Tune thresholds from observed baselines.
4. Match only the application's fixed `service`, `event`, and `level` fields for custom app alerts. If necessary, include a static environment name and aggregate count and time window. Keep out raw errors, request bodies and URLs, callback query strings, headers, cookies, credentials, object keys, UUIDs, titles, personal details, photos and recordings. Keep authentication callbacks out of raw exported logs unless the provider can strip sensitive fields before export. Check the final message and destination storage, including excerpts and attachments, for redaction. Vercel runtime logs may attach their own request metadata independently of app output. [Vercel runtime logs](https://vercel.com/docs/logs/runtime)
5. Trigger the provider's test notification or replay one `monitoring.synthetic` event into the approved isolated monitor. Use a rule that matches one event for this exercise. A generic 5xx anomaly rule might never fire for one event. Record actual recipient acknowledgement, delivery time, rule/environment, payload fields and any failure. Remove the temporary test rule once authorized. The local test has already verified the synthetic event's schema and receipt by a local sink. External receipt is pending.
6. On alert, the responder acknowledges and opens an incident with time, environment and sanitized symptom. Check recent changes, dependency status and the known recovery points. Preserve relevant evidence under restricted access. Escalate suspected account boundary failures immediately and contain access or writes through the authorized owner. Contact the database/storage owner to initiate a separate-target restore. Ask the founder and legal reviewer to decide whether communication or notifications are required. Record the incident outcome and retest the alert rule at review.

## Private media reconciliation

`scripts/private-media-inventory.sql` is a read-only, owner-scoped candidate report. Bind an authorized existing owner UUID and approved timestamp as PostgreSQL parameters `$1` and `$2` from a restricted operator session. Run first on disposable data. The query checks the private bucket, path format, object age, current avatar, saved documents including drafts, and referenced workspace metadata. It excludes accounts marked for deletion. Keep candidate keys only in the restricted operations workspace. An empty result from a successful query means that this inventory found no candidates for the specified active owner. A failed query means stop.

An old content-addressed key can be reused by a new upload without changing its timestamp. Even two matching inventory snapshots cannot prove absence while writes are active. Keep this report read-only until an authorized operator can pause all writers for the scoped owner, including preview and background writers, and drain active requests. Keep the verified backup and document the pause. Rerun the report in a fresh successful read while writes remain paused. Intersect the new results with the reviewed candidates and stop on unexpected changes, unavailable references or uncertain state. Only a separately approved operation may remove those explicit keys through the Storage API, within the scoped prefix and private bucket. SQL deletion from Storage metadata would leave the actual bytes behind. Recheck active references, restore representative live files, check another fictional account, and resume writes after verification. [Supabase Delete Objects](https://supabase.com/docs/guides/storage/management/delete-objects)

Account closure has its own cleanup path. A save or avatar request already packing bytes can overlap deletion and may leave file bytes after the owner row is removed. The operator should investigate a closed prefix only after verifying the deletion request, the account state and the absence of remaining writers. Keep closed-prefix handling separate from ordinary attachment cleanup. No production cleanup schedule or irreversible operation is included in this phase.
